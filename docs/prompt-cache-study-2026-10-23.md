# RCode / DSH 缓存实测与优化记录

日期：2026-10-23（Asia/Shanghai）。模型：`deepseek-v4.1-flash`。服务：`https://dawan.fan`。

## 结论与证据范围

RCode 的请求格式没有 85% 的命中率上限。保持前缀稳定时，真实请求已达到 98.74%；确定工具顺序后的请求达到 99.26%。这不能推出所有生产会话都将保持 99%：累计统计包含冷启动，实际任务的新增内容、工具变更、压缩、请求间隔和服务端路由都会影响结果。

第一批执行 41 次付费模型请求，全部 HTTP 200；其中 35 次 Chat Completions、6 次 Messages。HTTP 成功不等于任务成功，部分短输出上限实验被截断，另有上下文识别错误，均保留原始记录。35 次 Chat 请求共上报 507,969 输入 token。22 次请求提供 `cost`，该字段合计 0.016558368；其余请求使用 `credit` 或不提供费用，不能把这个部分合计当成总费用。随后追加 31 次验证，总计 72 次；追加结果见“补充验证”，没有改动先前的原始记录。

两个实现采用相同模型、服务和匹配的文本/工具夹具，比较请求组织和序列化。RCode 请求来自实际 `NativeHarness` 向本地 HTTP 模拟服务发送的请求；DSH 直接运行其 `serialize.ts` 和 `replay.ts` 经类型擦除后的函数，仅替换框架错误类，图片路径在探针中明确禁用。没有运行完整 DSH 插件图或两个桌面应用的同任务自动化，也没有复现用户原有的 85% 会话。

DSH 源码为 `D:\projects\deepseek-harness`，提交 `687f282e86`。系统提示词组装、运行上下文投影、Messages 序列化和会话统计四个关键文件，与资料目录内的副本一致。

## 用户决策：不引入 in-history 专用机制

2026-10-23，用户明确认为 `in-history` 机制绑定过强，不增加相同的逻辑判断。本次方案撤回历史 system 更新：不新增 `systemPromptUpdate` 能力字段、按模型或路由启用的判断及对应序列化分支，也不通过删除能力判断来无条件追加历史 system。动态系统指令继续采用现有头部更新方式，内容真正变化时接受必要的缓存重建。

下文保留历史 system 实验数据作为研究证据，不再将该项列为待批准的落地方案。为该机制专门设计的持久化、恢复和压缩改造一并移出本次范围。事实类上下文追加当时保留为候选；后续用户确认接入后，已按普通内部提醒的需要实现其生命周期，见 [当前实现](context-reminders.md)。工具稳定排序和 usage 兼容不受此决定影响。

## 服务端观测限制

1. 相同 request hash 多次返回不同输入数量和 usage 格式。例如 #3/#4/#6/#8 同一个长请求，上报输入分别为 13,293、13,313、13,313、13,293；缓存读取从 0 到 13,184/13,056。另一个相同请求出现 15,685 与 17,461 两种输入数量。这说明网关侧的转换、路由或统计存在变化；具体是哪一种，客户端证据不能确定。
2. 第一批 6 次流式 Messages 请求没有返回缓存读取/写入计数。增加三个 `cache_control` 断点也没有恢复这些字段。补测发现部分非流式响应的 `data` 封装中有完整缓存计数，另一路响应仍缺失。应区分流式/非流式和响应形态，不能笼统判断整个接口都不可观测。
3. 35 次 Chat 请求中有 2 次未返回缓存计数。其余样本存在标准缓存字段和零值别名并存的情况，必须优先读取标准字段。
4. 初始相同请求重发有时仍为 0，随后才达到 98%～99%。不能以一次“冷/热”对照排除路由或缓存写入延迟。
5. 时延记录的是收到首个响应字节及完整响应的耗时，包含网络和排队；不是经过隔离的模型 TTFT 性能基准。

## 实测结果

### 固定工具顺序：已实施

实验保持 13 个工具的名称、描述和 schema 不变，仅改变顺序。大部分文本来自 RCode 实际生产提示词，追加合成的只读记录作为长历史夹具。

| 请求 | 操作 | 输入 | 缓存读取 | 命中率 |
|---|---|---:|---:|---:|
| #14～16 | 相同确定顺序 | 17,461 | 17,332 | 99.26% |
| #17 | 只逆转工具排列 | 15,685 | 0 | 0% |
| #18 | 重发逆序版本 | 17,461 | 0 | 0% |
| #19 | 将逆序版本恢复为确定顺序 | 17,461 | 17,332 | 99.26% |
| #41 | 使用修改后生产代码导出的工具定义 | 17,461 | 17,332 | 99.26% |

该实验验证的是工具顺序变化可以破坏已有缓存，以及确定顺序可以消除这种差异。没有证据证明用户原有会话的工具顺序每轮都在变化，因此不能把整个 85%→99% 差额归因于这个问题。

实现位于 `crates/model/src/prompt_cache.rs::ordered_tools`，在 Chat Completions、Responses 和 Anthropic 三个 provider 的请求序列化处复用。只排序工具定义引用，不修改原始注册表，不删工具，不改 schema，不重排历史中的工具调用或工具结果。

功能验证：三个协议的不同注册顺序生成完全相同的请求，逐个验证名称、描述、完整 schema 和数量。真实请求 #39/#40 在原顺序、确定顺序下均返回一个 `Read` 调用，参数均为 `file_path=C:/cache-study/fixture.txt, offset=3, limit=5`。实验没有执行文件工具。排序改变现有请求的工具前缀时，首次使用新顺序仍可能发生一次缓存重新建立。

### usage 兼容：已实施，属于统计完整性修复

实际网关响应 #11 同时包含：标准 `prompt_tokens_details.cached_tokens=15488`、`prompt_cache_hit_tokens=15488`、`cache_read_input_tokens=0`、`cached_tokens=0`。后两者是这条响应中的零占位，不能覆盖标准字段。

Chat 适配器保持原有优先级：标准字段 → `prompt_cache_hit_tokens`，然后才在前者缺失时兼容 `cache_read_input_tokens`、`cached_tokens`。同时保留服务端明确提供的 `cache_creation_input_tokens`。`prompt_tokens` 仍然是包含缓存子集的总输入，不重复相加；字段缺失继续保留未知，标准字段明确为 0 时不被其他别名覆盖。

这项修改不会提高服务端真实命中率，也不修改模型请求。它改善兼容网关的缓存计数保留。现有样本中的标准字段原本就能读取，不把这一项包装成本次网关上的命中率提升。

### 动态上下文后置：有效候选，未应用到生产

比较 system 尾部改写运行事实与在历史末尾追加运行事实。两组先验证 OAK，再依次更新为 PINE、BIRCH、CEDAR。保存真实历史回复与可用的推理内容。用于验证事实更新的配对请求都设置 `tool_choice=none`、`max_tokens=1024`；这是隔离实验参数，没有修改产品默认设置。

| 请求 | 位置 / 当前值 | 命中率 | 实际回复 |
|---|---|---:|---|
| #28 | system / OAK，预热对照 | 99.15% | OAK |
| #29 | 历史尾部 / OAK，预热对照 | 99.15% | OAK |
| #30 | 改写 system / PINE | 未上报 | PINE |
| #31 | 追加历史 / PINE | 98.96% | PINE |
| #32 | 改写 system / BIRCH | 0% | PINE（错误） |
| #33 | 追加历史 / BIRCH | 93.39% | BIRCH |
| #34 | 改写 system / CEDAR | 0% | 表示没有运行代码（错误） |
| #35 | 追加历史 / CEDAR | 93.20% | CEDAR |

请求本身确认 system 中包含对应新值，但网关输入计数和用量格式也发生了变化。因此，不能仅凭这组实验把错误回答归因于模型、网关或某个指令位置。它证明的是在该夹具里历史追加方案保持了较高命中，且正确读取了三次更新；尚未验证真实项目记忆、MCP 指令、恢复会话、撤销、压缩和子智能体的完整行为。

当时提出的事实类上下文候选范围（不包含历史 system 更新；当前落地范围另见实现文档）：

- 将可变的运行事实与固定操作规则分开。固定规则保留 system；记忆索引等事实只在内容变化时追加一个命名快照。
- 快照作为模型历史持久化，恢复会话时原样回放；后续变化追加新快照，不改写旧快照，也不每次重复无变化内容。
- 移除或清空内容也要有明确的新快照，避免旧事实继续生效。
- MCP 中真正的系统指令不能统一降为 user 消息。保留现有头部 system 更新，不新增 `in-history` 能力判断或发送路径。
- 测试记忆写入/关闭、MCP 重连、恢复、压缩、取消/重试、子会话隔离与历史回放，并再做同服务的连续请求对照。

这一项会改变模型看到信息的位置及历史持久化方式，按用户要求只记录实验，没有移入 RCode 生产路径。

### DSH 历史 system 更新：第一批兼容性探针

调用 DSH 原始序列化函数生成历史 system 更新。第一批 #36 经 Messages 接口返回 BETA，符合新系统快照内容，HTTP 200。该流式样本没有缓存字段。后续非流式补测已获得缓存收益证据，见下一节；仍不足以为所有模型默认启用该能力。

## 补充验证：将“未知”细分为可测结果和剩余边界

用户追问收益不明确是否完全无法验证后，继续执行 31 次真实调用：15 次 Chat、16 次 Messages，全部 HTTP 200，27 次具有可用缓存计数。补充编号 S1～S31 对应 `output/cache-study/2026-10-23/supplementary/` 中的文件。两个早期探针因输出上限结束，没有产出答案，不能作为行为验证成功。

### 找到非流式观测入口

部分 Messages 非流式响应不是标准 Messages 对象，而是 `{success: true, data: <Chat completion>}`。`data.usage` 包含缓存字段，`data.model` 还显示了实际响应的上游标识。补充 S1 的原始响应已完整保存；发现封装后修正了该记录的派生统计，并注明恢复来源，原始响应未改变。实验库已增加封装解析和回归测试。

这修正了第一批的证据边界：当时流式响应缺计数，不等于该优化完全无法验证。非流式响应仍有另一种直接返回 Messages 对象、缺缓存计数的形态。流式与非流式可能使用不同转换路径，不能把非流式读数当作每一条流式请求的测量值。

### 三个小项的交叉对照

| 项目 | 实验设计 | 实测结果 | 可以下的结论 |
|---|---|---|---|
| 缓存断点 | S1～S6，无断点/三个断点各 3 次；使用已预热的同一内容，交换执行顺序 | 每组 2 次有完整计数，均为 17,332 / 17,461 = 99.26%；每组 1 次缺计数 | 可观测响应组的预热缓存续用没有额外收益；没有覆盖冷启动建缓存速度和所有路由 |
| 会话请求头 | S7～S15，不传、固定、每次变化的 `x-session-id` 各 3 次，交叉执行 | 9 次全部为 17,332 / 17,461 = 99.26% | 本批没有额外命中收益；不能据此断言网关永久忽略请求头或没有任何路由作用 |
| usage 选项 | S16～S21，省略/设置 `include_usage` 各 3 次，交叉执行 | 全部有 usage；17,461 输入组均为 99.26%，15,685 输入组均为 98.74% | 相同输入计数组内缓存结果一致，本服务不依赖该选项返回计数；其他服务兼容性需独立判断 |

没有将这些项目改入产品默认配置。这里的结论是“当前条件下未观察到额外收益”，而不是“任何条件下都没有收益”。时延样本仍包含排队和网络波动，不据此做速度提升结论。

### 保留 system 优先级的历史更新：已量化收益，已决定不采用

使用 DSH 原始序列化函数，固定同一段合成记录和消息历史，只改变路由的 `systemPromptUpdate` 能力：一组把最新系统快照放到头部，另一组保留初始头部并将新系统快照追加到历史。公开的工作目录从 alpha 连续改为 beta、gamma、delta；要求模型解析 `config.json` 的绝对路径，不执行任何文件操作。与第一批“运行代码”探针不同，本例明确说明配置是可向用户公开的事实。保留返回的可用推理内容，输出上限为 1024。

## 其他优化点的处置

| 项目 | 发现 / 结果 | 处置 |
|---|---|---|
| 固定日期、环境、项目规则 | RCode 已有持久化冻结快照 | 保留；不重复实现 |
| 动态记忆、MCP 说明 | 原方案位于历史之前，变化会改写前缀 | 已接入可明确分类的事实索引增量及 MCP 状态通知；记忆规则、保留条目、MCP 指令正文仍在 system；历史 system 方案继续排除 |
| 工具集合 / schema 变化 | 排序只能解决顺序，不能让变更后的定义等同于旧定义 | 不隐藏真实能力变化；增量/延迟工具声明需独立兼容性验证 |
| 显式 `cache_control` | 补充交叉实验的可观测响应组，开启/关闭均为 99.26% | 预热续用未见额外收益；未增加断点或改默认缓存模式 |
| `stream_options.include_usage` | 补充 6 次交叉请求全部返回 usage，相同输入计数组内命中率一致 | 未见命中收益，未改产品默认请求 |
| `x-session-id` 路由亲和 | 补充 9 次交叉请求，无/固定/变化请求头均为 99.26% | 未见命中收益，未新增请求头；不是对所有路由行为的否定 |
| 删除推理 / 摘减历史 | 资料目录的优化器确有内容损失；DSH 原版保留推理 | 不移植这种减损转换，不作为无损缓存优化 |
| 压缩阈值、上下文长度 | 会影响记忆保真、窗口压力和新增 token 比例 | 未修改；本轮没有长期任务效果证据 |
| 跨会话共享、缓存 TTL | 与上游模型、网关和隔离规则有关 | 不凭客户端百分比修改供应商策略 |
| 统计口径 | 两边会话面板都按输入 token 加权；冷启动影响累计值 | 保持公式，缺失计数继续显示未知 |
| 模型/协议切换 | 同一模型名有不同响应形态；Messages 非流式的部分响应可读取嵌套缓存计数 | 非流式作为诊断入口，不把协议/流模式切换作为产品优化 |
